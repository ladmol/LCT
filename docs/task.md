# Фалькон Тех — Техническое задание (2026)

Сервис формирования цифрового признака транспортного средства для сопоставления снимков одного автомобиля из разных локаций без использования государственного номера.

> Источник: `7. Фалькон Тех.pdf` (оригинал), перенесено в Markdown для удобства ревью в git.

## 1. Термины и определения

- **ReID (Re-Identification)** — задача повторной идентификации конкретного объекта (автомобиля) на изображениях, полученных с разных, непересекающихся камер наблюдения.
- **Open-set Retrieval (поиск в открытом множестве)** — подход, при котором модель должна уметь обобщать свои знания и корректно работать с ранее не виденными автомобилями, а не просто классифицировать их по заранее известному, фиксированному списку.
- **Эмбеддинг (Embedding)** — векторное представление визуальных признаков объекта фиксированной размерности, которое позволяет математически сравнивать схожесть разных изображений.
- **Bounding Box (BBox)** — координаты ограничивающего прямоугольника, который выделяет транспортное средство в кадре. Эти координаты предоставляются участникам заранее, чтобы сфокусировать задачу именно на идентификации, а не на поиске объекта.
- **Режим отказа (Refusal)** — важная продуктовая способность сервиса вернуть пустой ответ или сообщение о невозможности идентификации, если в базе данных (галерее) нет уверенного совпадения с запросом, вместо того чтобы выдавать ложноположительный результат.

## 2. Контекст и актуальность задачи

Современная городская инфраструктура располагает разветвлённой сетью камер, которые ежедневно фиксируют миллионы транспортных средств. Традиционный метод идентификации через ALPR (автоматическое распознавание номера) имеет серьёзные физические ограничения: номер может быть нечитаемым из-за загрязнения, погодных условий, бликов, перекрытия другим объектом или отсутствия в кадре.

В таких ситуациях ручной поиск целевого автомобиля оператором по архивным записям превращается в трудоёмкий процесс (сотни-тысячи часов, часто безуспешный). Городу и службам безопасности требуется сервис, формирующий устойчивый цифровой признак (вектор) автомобиля на основе визуальных характеристик (цвет, тип кузова, геометрия, наклейки, повреждения), позволяющий сопоставлять снимки одного и того же ТС с разных камер без привязки к номеру.

## 3. Концепция и целевые задачи

Задача формулируется как **поиск по изображению (image retrieval) в открытом множестве**. Участникам даётся галерея (набор изображений ТС с известной идентичностью) и запрос (изображение ТС, идентичность которого нужно установить).

Решение должно выполнять:

1. **Формирование признака** — извлечение информативного эмбеддинга из изображения ТС, обрезанного по предоставленным координатам BBox.
2. **Ранжирование** — упорядочивание объектов галереи по убыванию вероятности, что это то же самое ТС.
3. **Режим предложения кандидатов** — возврат списка вероятных совпадений с оценкой уверенности, либо пустой ответ (отказ), если уверенного кандидата нет. Порог отсечения определяется участниками самостоятельно и обосновывается на защите.

**Важно:** в задачу **не входит** детекция ТС, распознавание номеров и трекинг. Координаты BBox предоставляются вместе с данными как на обучающей, так и на тестовой выборке.

## 4. Функциональные требования

Работа сервиса разделена на последовательные этапы:

- **Этап получения** — приём изображения и координат BBox через API/UI, базовая валидация входных данных.
- **Этап обработки** — извлечение визуальных признаков: генерация векторного эмбеддинга фиксированной размерности (например, float32), опционально — классификация дополнительных атрибутов ТС.
- **Этап анализа** — векторный поиск: сравнение эмбеддинга запроса с базой галереи (косинусное сходство или L2 по нормированным векторам). Векторы одного ТС с разных камер должны быть математически ближе друг к другу, чем векторы разных ТС.
- **Этап результата** — сортировка кандидатов по убыванию близости; возврат топ-N кандидатов или пустой ответ, если максимальная оценка ниже порога (режим отказа).

## 5. Требования к предоставляемым данным

1. **Формат изображений** — полные кадры JPEG/PNG в исходном разрешении камеры. Плоский каталог `images/` со случайными идентификаторами в качестве имён файлов.
2. **Аннотации** — в отдельных CSV (`train.csv`, `test.csv`): `image_id`, координаты BBox (`x, y, w, h` в пикселях исходного кадра), `vehicle_id` (уникальный идентификатор идентичности, доступен только для обучающей выборки). Один кадр может содержать несколько размеченных ТС. `camera_id`, время съёмки и геопривязка участникам **не передаются** — задача решается исключительно по визуальным признакам.
3. **Анонимизация** — государственные номера и лица людей на всех кадрах преднамеренно размыты. Использование любых остаточных признаков номера — строго запрещено.
4. **Разметка идентичности (Open-set)** — множества `vehicle_id` в train/test гарантированно не пересекаются. На тесте — только ранее не виденные автомобили.
5. **Покрытие условий** — разное время суток, погодные условия, ракурсы (фронт/бок/зад), частичное перекрытие, низкое качество. Каждое ТС в тестовой выборке снято минимум с двух точек наблюдения.

Датасет доступен по ссылке в личном кабинете; подробности — в `README.md` внутри архива с данными.

## 6. Требования к архитектуре, коду и сборке решения

- **Микросервисная архитектура** — чёткое разделение backend инференса, БД, клиентской части.
- **Технологический стек** — backend на Python, C++ или Rust; предпочтение свободному ПО / реестру отечественного ПО, работающему под Linux.
- **Хранение данных** — реляционная, документо-ориентированная или специализированная векторная СУБД (например, PostgreSQL+pgvector, FAISS, Milvus) для эмбеддингов и метаданных галереи.
- **API и интерфейс** — все методы формализованы через OpenAPI (Swagger). Доступ пользователя — через веб-браузер (тонкий клиент).
- **Контейнеризация** — все компоненты в Docker; репозиторий обязан содержать `Dockerfile` и `docker-compose.yml`, запуск одной командой без ручных манипуляций.
- **Качество и воспроизводимость кода** — открытый, не обфусцированный код с понятными комментариями, строго соответствующий документации. По запросу жюри — демонстрация сборки/исполнения в реальном времени.

## 7. Производительность и внешние ресурсы

- **Тестовое оборудование** — единое для всех участников, предоставляется организаторами (конфигурация GPU/RAM сообщается перед хакатоном).
- **Метрики производительности** — время формирования признака на одно ТС (батч=1); общая пропускная способность (FPS) при пакетной обработке без очередей и деградации памяти.
- **Ограничения по ресурсам** — суммарный размер весов модели ≤ **2 ГБ**. Потребление RAM при инференсе не должно приводить к OOM на тестовой выборке.
- **Порядок проверки** — финальные замеры проводят организаторы самостоятельно стандартизированным скриптом. Собственные замеры участников — справочные, не влияют на баллы.
- **Внешние ресурсы** — публичные предобученные веса и открытые датасеты разрешены и приветствуются, но должны быть перечислены в `Readme.md`. Решения на закрытых/проприетарных/невоспроизводимых данных — **не допускаются к оценке**.

## 8. Формат сдачи результата

- **`submission.csv`** — для каждого запроса упорядоченный список идентификаторов галереи, топ-10 кандидатов по убыванию близости.
- **`embeddings.npy`** — матрица векторов для всех объектов тестовой выборки, в порядке, строго соответствующем выданному CSV.
- **`candidates.csv`** — результат «режима предложения кандидатов»: для каждого запроса — принятые кандидаты с оценкой уверенности, либо пустой ответ (отказ).
- **Код и окружение** — исходный код обучения и инференса, `Dockerfile`, `docker-compose.yml`, файл зависимостей. Инференс — одной командой в изолированном окружении, **без доступа в интернет** (все веса — в составе решения).

**Механика оценки:** проверка вручную организаторами по завершении хакатона, на закрытой части тестовой выборки, эталонным скриптом расчёта метрики (предоставляется участникам заранее).

## 9. Критерии оценки

При оценке совпадения **в пределах одной камеры исключаются** — засчитываются только кросс-камерные сопоставления (суть задачи ReID).

- **Основная метрика** — mAP (mean Average Precision) по всем запросам.
- **Дополнительные метрики** (отдельными столбцами) — Rank-1, Rank-5.
- **Режим предложения кандидатов** оценивается по:
  - **F1-score** при пороге, выбранном командой — основная метрика режима;
  - **TNR (True Negative Rate)** — доля корректных отказов на запросах без совпадения в галерее;
  - **mINP или AUC** по кривой Precision-Recall — качество разделения «совпадение/несовпадение» независимо от порога.

### Итоговая оценка

| Критерий | Вес |
|---|---|
| Точность на закрытом тесте (mAP на скрытой части выборки) | 45% |
| Производительность и применимость (скорость на оборудовании организаторов, размер весов) | 20% |
| Инженерное качество (воспроизводимость, архитектура, Docker, документация) | 15% |
| Корректность режима предложения кандидатов (F1-score, TNR) | 10% |
| Защита решения (питч, обоснование архитектуры и порога отказа) | 10% |

**Дисквалификация:** решения, не воспроизводящиеся из предоставленного кода, либо использующие признаки государственного номера.

## 10. Дополнительные возможности (тай-брейкер)

Используются жюри только при равенстве основных метрик у нескольких команд — не добавляют баллов к сумме 100%:

- **Демонстрационный веб-интерфейс** — загрузка запроса, визуализация ранжирования, оценка уверенности, экспорт результатов.
- **Интерпретируемость модели** — визуализация (Grad-CAM/Attention maps) областей изображения, повлиявших на решение.
- **Масштабируемость** — приближённый поиск ближайших соседей (ANN, FAISS/HNSW) для галереи порядка 10^6 объектов.
- **Глубокий анализ ошибок** — разбор характерных неудачных сопоставлений в документации/питче.
