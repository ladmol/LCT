# Технологический стек и требования к мощностям — Vehicle Re-ID (Falcon Tech, ЛЦТ 2026)

Документ описывает выбранные технологии по каждому компоненту пайплайна, требования к вычислительным ресурсам (обучение и инференс), оценочную latency по стадиям и рекомендации по железу для хакатона.

Состав компонентов соответствует зафиксированной архитектуре пайплайна (см. `docs/architecture.md`); здесь описываются только технологии, мощности и тайминги, без деталей архитектурных решений.

## 1. Технологический стек по компонентам

| № | Компонент | Технология/библиотека | Язык | Почему выбрано (кратко) | Альтернативы |
|---|-----------|------------------------|------|--------------------------|---------------|
| 1 | Детекция ТС | YOLOv8n / YOLOv8s (Ultralytics), претрейн без дообучения | Python | Готовые веса, класс "car/truck/bus" уже есть в COCO, высокая скорость, минимум усилий на интеграцию | YOLOv8m/l (точнее, медленнее), YOLOv5, RT-DETR |
| 2 | Трекинг (опционально, для видео) | ByteTrack / DeepSORT | Python | Лёгкая интеграция с Ultralytics (`model.track`), не требует переобучения, устойчив к кратковременным перекрытиям | BoT-SORT, OC-SORT, StrongSORT |
| 3 | Кроп + препроцессинг | OpenCV | Python | Индустриальный стандарт для CV-препроцессинга (crop, resize, normalize, color-space), быстрый, без зависимостей от GPU | Pillow, torchvision.transforms |
| 4 | Re-ID модель (embedding) | PyTorch + FastReID (JDAI-CV) или torchreid; бэкбоны OSNet/ResNet50 (лёгкий) vs TransReID/ViT (точнее) | Python | Готовые пайплайны обучения/инференса Re-ID "из коробки", предобученные веса на Re-ID датасетах, гибкий выбор баланса скорость/точность | timm + кастомный training loop, PaddleReID |
| 5 | Атрибутные головы (цвет/тип кузова/ракурс) | Доп. классификаторы (та же backbone + FC-головы) или classical CV (color histogram, k-means по HSV) | Python | Простая надстройка над эмбеддером, не требует отдельной тяжёлой модели; classical CV — быстрый fallback без обучения | Отдельная лёгкая CNN (MobileNet) под атрибуты |
| 6 | Vector DB | Qdrant (Docker, HNSW, payload-фильтры) — основной вариант; FAISS — fallback | Python (клиент) / Rust (сервер Qdrant) | Qdrant даёт готовый REST/gRPC API, фильтрацию по метаданным вместе с ANN-поиском, персистентность из коробки; FAISS проще поднять локально без сервера для быстрого прототипа | Milvus, ChromaDB, pgvector |
| 7 | Метаданные | PostgreSQL (основной вариант) или SQLite (для локального демо) | SQL | PostgreSQL — надёжность и совместные джойны с payload-фильтрами; SQLite — нулевая настройка для демо на одной машине | MongoDB (документная модель) |
| 8 | Backend API | FastAPI | Python | Автогенерация OpenAPI/Swagger, асинхронность, быстрая разработка REST-эндпоинтов, нативная интеграция с Pydantic-валидацией | Flask, Django REST Framework |
| 9 | Frontend/демо | React + TypeScript (Vite), пакеты через pnpm | TypeScript | Полноценный SPA поверх REST API без ограничений быстрых прототипов (Streamlit/Gradio), стандартный для frontend-разработки стек | Streamlit/Gradio (быстрее собрать, но менее гибкий UI), Next.js, Vue |
| 10 | OCR номера (когда читаем) | EasyOCR или PaddleOCR | Python | Готовые модели распознавания текста на изображении без дообучения, работают "из коробки" на кропах номерных знаков | Tesseract, кастомный CRNN |
| 11 | Экспорт/оптимизация модели | ONNX Runtime / TensorRT (опционально) | Python/C++ (рантайм) | Ускорение инференса детектора и Re-ID модели за счёт графовой оптимизации и (для TensorRT) FP16/INT8 квантизации | OpenVINO (для CPU-инференса на Intel) |

**Версия Python: 3.13**, зафиксирована в `backend/.python-version` и `ml/.python-version` (пакеты через uv). Проверено фактическим резолвом зависимостей (`uv pip compile`) по всему стеку сразу: под Python 3.14 не собирается **PaddlePaddle** (нет колёс под `cp314`, максимум — `cp313`), а вместе с ним и рабочий бэкенд PaddleOCR — весь остальной стек (torch/torchvision, opencv-python, ultralytics, easyocr, onnxruntime, faiss-cpu, qdrant-client, psycopg, sqlalchemy, fastapi, uvicorn, streamlit, gradio) под 3.14 собирается без проблем. 3.13 — самая новая версия, под которую резолвится весь список целиком без потери PaddleOCR как опции.

## 2. Требования к вычислительным мощностям (compute)

### 2.1 По компонентам

**1. Детекция ТС (YOLOv8n/s)**
- Обучение/дообучение: не требуется — используется претрейн на COCO без файнтюнинга.
- Инференс: CPU приемлем для демо (сотни мс/кадр на YOLOv8n), GPU (даже начального уровня, 4GB+) даёт near-real-time (десятки мс/кадр).

**2. Трекинг (ByteTrack/DeepSORT)**
- Обучение: не требуется (алгоритмический трекер поверх детекций, не нейросеть с обучением под задачу; DeepSORT использует готовый re-id embedder для appearance-фичи).
- Инференс: чисто CPU-нагрузка (обработка боксов, венгерский алгоритм, каскадное сопоставление), нагрузка минимальна по сравнению с детекцией/эмбеддингом.

**3. Кроп + препроцессинг (OpenCV)**
- Обучение: неприменимо.
- Инференс: только CPU, нагрузка пренебрежимо мала (единицы мс на кроп/ресайз).

**4. Re-ID модель (embedding extraction)**
- Обучение/дообучение:
  - OSNet/ResNet50 на VeRi-776: достаточно 1 GPU с 8GB VRAM (например RTX 3060/T4). Датасет некрупный (~50k изображений, 776 идентичностей) — обучение занимает единицы часов (ориентировочно 2–6 часов на 60–120 эпох на T4/RTX3060 при batch size 32–64).
  - TransReID/ViT: рекомендуется GPU от 16GB VRAM (ViT-Base требователен к памяти при батчах и attention), обучение дольше — ориентировочно 6–12+ часов на том же датасете на T4/3060, на более мощной GPU (A100/3090/4090) — быстрее.
  - Файнтюн на VehicleX/VeRi-Wild/CityFlow — сопоставимые или чуть большие требования из-за объёма данных (VeRi-Wild крупнее — время обучения растёт пропорционально).
- Инференс:
  - OSNet/ResNet50: CPU приемлем для демо (~50–100мс/кроп), GPU — единицы-десятки мс/кроп.
  - TransReID/ViT: заметно медленнее на CPU (может быть неприемлемо для интерактивного демо), на GPU — приемлемо для near-real-time.

**5. Атрибутные головы**
- Обучение: лёгкая FC-голова поверх готового backbone — дообучение быстрое (десятки минут — 1-2 часа на GPU уровня T4 при наличии размеченных атрибутов); classical CV (гистограммы) — обучения не требует вовсе.
- Инференс: пренебрежимая доп. нагрузка поверх основного forward pass эмбеддера (доли мс — единицы мс), classical CV — CPU, единицы мс.

**6. Vector DB (Qdrant/FAISS)**
- Обучение: неприменимо (не ML-модель).
- Инференс/работа: чистый CPU. Для масштаба хакатон-демо (тысячи — десятки тысяч записей) требования к RAM минимальны (обычно достаточно 1-2GB под индекс + оверхед), диск — единицы-десятки МБ на 10k эмбеддингов (при размерности вектора 512-768).

**7. Метаданные (PostgreSQL/SQLite)**
- Чистый CPU, минимальные требования к RAM/диску на объёме демо-данных (десятки тысяч записей — единицы-десятки МБ).

**8. Backend API (FastAPI)**
- Чистый CPU, минимальные требования; основная нагрузка — проксирование к ML-инференсу и Vector DB, а не сам API-слой.

**9. Frontend/демо (React + TS, Vite)**
- Чистый CPU, требования минимальны, работает на любом ноутбуке.

**10. OCR (EasyOCR/PaddleOCR)**
- Обучение: не требуется — готовые претрейн-модели.
- Инференс: CPU приемлем для демо (сотни мс на изображение), GPU ускоряет до десятков мс.

**11. Экспорт/оптимизация (ONNX Runtime/TensorRT)**
- Требует GPU только на этапе конвертации/калибровки (для TensorRT INT8-калибровки желательна GPU), после экспорта инференс возможен и на CPU (ONNX Runtime CPU EP) с приростом скорости относительно "сырого" PyTorch.

### 2.2 Сводная таблица

| Этап | Нужна ли GPU | Мин. конфигурация | Комментарий |
|------|--------------|--------------------|-------------|
| Обучение/дообучение OSNet/ResNet50 (VeRi-776) | Желательна | 1×GPU 8GB (RTX 3060/T4) | Часы, не дни; альтернатива — бесплатный Kaggle/Colab T4 |

## 3. Оценка времени обработки (latency)

Оценки грубые, порядка величины, не точные бенчмарки — фактические цифры зависят от разрешения входного изображения, версии библиотек, драйверов и конкретного железа. Допущения: один автомобиль/кадр на выходе детектора, разрешение кадра ~720p-1080p, эмбеддинг размерности 512-768, база — 10-50k векторов в Qdrant/FAISS с HNSW-индексом, батч = 1 (единичный запрос, не батч-обработка).

| Стадия пайплайна | CPU-инференс | GPU-инференс | Комментарий |
|---|---|---|---|
| Детекция (YOLOv8n) | ~80–150 мс | ~15–30 мс | Основные затраты — на препроцессинг + forward pass |
| Кроп + препроцессинг (OpenCV) | ~2–5 мс | ~2–5 мс (CPU-bound операция) | Не зависит от наличия GPU |
| Embedding extraction (OSNet/ResNet50) | ~50–100 мс | ~5–15 мс | На батч из нескольких кропов время растёт медленнее линейного за счёт батчинга на GPU |
| Embedding extraction (TransReID/ViT) | ~150–300 мс+ | ~15–40 мс | ViT существенно тяжелее на CPU |
| ANN-поиск (Qdrant/FAISS, 10-50k векторов) | единицы мс (~1–10 мс) | — (обычно CPU-операция) | HNSW-индекс работает на CPU даже при GPU-инференсе моделей |
| Re-ranking (доп. попарное сравнение top-K кандидатов) | ~5–40 мс | ~5–40 мс (если реализовано векторно на GPU) | Зависит от размера K (top-20 vs top-100) и метода (косинусная близость vs более сложные метрики) |
| OCR номера (EasyOCR/PaddleOCR) | ~200–500 мс | ~30–80 мс | Выполняется опционально, не на каждом кадре, а на кропе с читаемым номером |
| **Итого "тяжёлый" путь без OCR** (детекция → кроп → embedding → ANN) | **~135–255 мс** | **~25–60 мс** | Ориентир для одного объекта на кадр, без трекинга/батчинга |

Замечания:
- Приведённые цифры — порядок величины для планирования архитектуры демо, а не результат профилирования на конкретном железе; перед защитой рекомендуется прогнать реальный бенчмарк на используемом стенде.
- При обработке видео с трекингом (ByteTrack/DeepSORT) не обязательно считать эмбеддинг на каждом кадре для каждого трека — можно сэмплировать (например, раз в N кадров), что снижает суммарную нагрузку.
- TransReID/ViT для реального real-time на CPU, вероятнее всего, не подойдёт — для демо на CPU разумнее OSNet/ResNet50, TransReID — как "точный" режим при наличии GPU.

## 4. Рекомендации по железу для хакатона

| Задача | Рекомендация |
|---|---|
| Обучение/дообучение Re-ID модели | Один ноутбук/ПК с GPU 8GB+ (RTX 3060 и выше), либо бесплатные облачные GPU: Kaggle Notebooks (T4/P100, до 30ч/нед) или Google Colab (T4 бесплатно, с ограничениями по времени сессии) |
| Разработка backend/frontend, интеграция | Обычный ноутбук без GPU — FastAPI, React/Vite, работа с Qdrant/PostgreSQL через Docker не требуют GPU |
| Поднятие Qdrant + PostgreSQL локально | Docker / Docker Compose на любом ноутбуке разработчика — оба сервиса легковесны для объёма демо-данных |
| Демонстрация на защите | Желательно иметь хотя бы один ноутбук с GPU (даже 4-6GB) для near-real-time демо на видео; при отсутствии GPU — заранее предобработанные примеры + CPU-демо для показа "вживую" на некритичных кейсах |
| Инференс на CPU как fallback | Закладывать в архитектуру возможность полностью CPU-инференса (OSNet/ResNet50 + YOLOv8n) — на случай отсутствия GPU в момент защиты |
