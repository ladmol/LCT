# План разработки

Команда из двух человек, два параллельных трека:

- **A — ML/Data:** модель, валидация, порог, артефакты сдачи.
- **B — Backend/Infra/Frontend:** сервисы, Docker, UI, документация.

Архитектура — [`architecture.md`](architecture.md), ТЗ — [`task.md`](task.md).

## Принципы

1. **Сначала рабочий путь от начала до конца, потом качество.** Первая цель — `predict`, который из `test_query.csv` + `test_gallery.csv` выдаёт три валидных файла на предобученной модели без дообучения. Всё дальнейшее — итерации поверх работающего пути.
2. **Приоритет по весам оценки.**
   - mAP (45%) и скорость (20%) важнее всего остального.
   - Режим отказа (10%) делается на той же валидации почти бесплатно.
   - UI, Grad-CAM и ANN на 10⁶ дают 0 баллов (тай-брейкеры) и делаются в последнюю очередь.
3. **Единый `reid_core`.** Препроцессинг и постобработка пишутся один раз и используются в train, predict и сервисе. Любое расхождение между ними — баг.
4. **Метрики как у организаторов.** Наш `eval` считает mAP, Rank-1/5, F1, TNR и mINP по тем же правилам: кросс-камерно, open-set. Когда выдадут эталонный скрипт, сверяемся с ним.
5. **Воспроизводимость с первого дня.** Все веса и датасеты записываются в Readme сразу при появлении. Итоговый образ работает без сети.

## Фазы

Длительность — в процентах от времени хакатона: пересчитать в дни под фактическое расписание.

| Фаза | % времени | Трек A — ML/Data | Трек B — Backend/Infra/Frontend |
|---|---|---|---|
| **0. Сквозной бейзлайн** | 0–15 | Загрузка данных, кросс-камерный open-set сплит train (§6.1 архитектуры), `eval`. Предобученная модель (CLIP-ReID или ResNet50-IBN) без дообучения → `predict` → три файла | Каркас репозитория (`reid/`, `services/`, `frontend/`), ruff + pytest, `docker-compose.yml` с `db` (pgvector), заглушки `api`/`inference` с OpenAPI |
| **1. Основная модель** | 15–50 | Дообучение на train (+ открытые датасеты), аугментации, flip-TTA, k-reciprocal re-ranking. Сравнение backbone по mAP и скорости | `inference` на ONNX Runtime, `api`: `/v1/embed`, `/v1/search`, `/v1/gallery*`, загрузка тестовой галереи. Контейнер `predict` без сети с встроенными весами |
| **2. Отказ и скорость** | 50–70 | Калибратор `P(same)`, выбор τ по F1 на валидации с дистракторами, кривые PR/F1/TNR. Экспорт ONNX → TensorRT FP16, проверка, что mAP не просел | `benchmark` (батч=1 и пакетный FPS), профилирование декодирования и препроцессинга, `confidence` и `refused` в API |
| **3. Продукт и тай-брейкеры** | 70–85 | Разбор ошибок: ракурс, ночь, перекрытия, одинаковые модели машин. При запасе времени — ансамбль или дистилляция | UI: загрузка, bbox, выдача, отказ, экспорт CSV. Grad-CAM (`/v1/explain`). Бенчмарк FAISS на 10⁶ |
| **4. Сдача** | 85–100 | Финальные артефакты, метрики и обоснование τ в Readme | Прогон «чистый клон → `docker compose up`» на чистой машине, Readme, презентация |

## Точки синхронизации

| Точка | Когда | Что фиксируется |
|---|---|---|
| **m1** | конец фазы 0 | Интерфейс `reid_core`: `preprocess(image, bbox)`, `embed(batch)`, `rank(q, g)`, `calibrate(...)`; контракт API (§5 архитектуры); layout `predict` (пути, выходы) |
| **m2** | середина фазы 1 | Выбран backbone → зафиксированы размерность `D` и `input_size`; схема `gallery` в pgvector |
| **m3** | конец фазы 2 | Итоговые веса, ONNX/TRT, τ; `api` и `predict` работают на одном артефакте модели |
| **m4** | начало фазы 4 | Код заморожен; дальше только документация и презентация |

Между точками треки не ждут друг друга: B работает на заглушке `inference` (случайные L2-нормированные векторы нужной размерности), A — на своих скриптах.

## Критерии готовности (чек-лист сдачи)

**Артефакты (ТЗ §8, README датасета)**
- [ ] `submission.csv`: `query_id, gallery_id_1..10`, одна строка на каждую строку `test_query.csv`.
- [ ] `embeddings.npy`: `float32 [1110 + 750, D]`, сначала query, затем gallery, в порядке файлов.
- [ ] `candidates.csv`: `query_id, gallery_id, confidence`; запросы с отказом не дают строк.
- [ ] `predict` запускается одной командой в изолированном окружении без сети и принимает пути к произвольным CSV (закрытая часть теста).

**Качество**
- [ ] mAP, Rank-1, Rank-5, mINP на валидации (кросс-камерно, open-set) — в Readme.
- [ ] F1, TNR, PR-AUC при выбранном τ + кривые + обоснование τ — в Readme.

**Производительность**
- [ ] Суммарный размер весов ≤ 2 ГБ.
- [ ] `benchmark`: время признака при батче 1 и FPS в пакете; нет OOM на полном тесте.

**Инженерия (ТЗ §6, §12)**
- [ ] `docker compose up` поднимает `db`, `inference`, `api`, `frontend` без ручных шагов.
- [ ] OpenAPI (Swagger) доступен из `api`.
- [ ] Readme: архитектура, методы, инструкция сборки, метрики, обоснование порога, полный список библиотек, весов и датасетов с версиями.
- [ ] Код обучения в репозитории и воспроизводим.

**Защита (ТЗ §11)**
- [ ] Презентация: backbone и его обоснование, как решали ракурс и освещение, пользовательский путь, план масштабирования, честный разбор ошибок с примерами.

## Риски

| Риск | Что делаем |
|---|---|
| Переобучение на 1 541 ID train | Предобучение на открытых датасетах, open-set валидация по ID, ранняя остановка по валидационному mAP |
| Порог τ, подобранный на валидации, не переносится на закрытый тест | Калибровка вероятностей вместо «сырого» порога сходства, проверка устойчивости τ по фолдам и бутстрепу, доля дистракторов в валидации близка к тестовой |
| ViT слишком медленный на железе организаторов | ResNet50-IBN как резервный вариант с готовыми замерами; TensorRT FP16; решение по замерам, а не заранее |
| Модель выучит остатки номерного знака | Маскирование зоны номера как аугментация; Grad-CAM-проверка, что внимание не концентрируется на номере |
| Предобработка в сервисе и в `predict` разойдутся | Единый `reid_core`; тест: эмбеддинг одного кропа через `predict` и через `/v1/embed` совпадает до допуска |
| Не успеваем к сдаче | Сквозной бейзлайн в фазе 0 и сохранение валидных артефактов после каждой итерации; тай-брейкеры — только после m3 |
| Открытые вопросы к организаторам (§10 архитектуры) остаются без ответа | Задать в первый день; до ответа — консервативные допущения, записанные в Readme |
