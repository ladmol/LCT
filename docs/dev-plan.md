# План разработки — Vehicle Re-ID (Falcon Tech, ЛЦТ 2026)

## 1. Общий подход

Задача решается за ограниченное время хакатона, поэтому ключевой принцип — **не обучать ничего с нуля**. Берём готовый тулбокс FastReID с претрейн-весами на VeRi-776/VehicleID, при необходимости дообучаем/адаптируем под целевые данные, а не строим re-id модель заново. Детектор (YOLOv8) и OCR (EasyOCR/PaddleOCR) также используются как готовые претрейн-компоненты без обучения с нуля.

Второй принцип — **параллельная разработка, а не конвейер**: backend-сервис и интеграционный пайплайн разрабатываются одновременно с работой над ML-моделью, на моках (заглушках вместо реальных эмбеддингов/поиска), а не после того, как модель будет готова. Это снижает риск того, что к моменту сдачи не останется времени на интеграцию.

Третий принцип — **MVP-first**: сначала собирается сквозной работающий путь «фото → детекция → эмбеддинг → поиск похожих → топ-N с score», пусть и на бейзлайн-качестве, и только потом идёт улучшение метрик, атрибутов, re-ranking и UI. Работающий, пусть и грубый, end-to-end пайплайн на ранней стадии — приоритет выше, чем точность отдельного компонента.

Четвёртый принцип — **команда из двух человек, два параллельных трека, а не четыре роли по очереди**. Рекомендованные в условии задачи роли (менеджер проекта, backend-разработчик, ML-инженер, специалисты по работе с данными) при команде из двух человек объединяются в два трека, идущих **одновременно**, а не последовательно передающих друг другу результат:

- **Трек A — ML/Data** (объединяет роли ML-инженера и специалиста по данным): детектор, Re-ID модель, атрибутные головы, датасеты, метрики качества.
- **Трек B — Backend/Infra/Frontend** (объединяет роль backend-разработчика; задачи менеджера проекта — координация на точках синхронизации, сборка демо-сценариев и питча — выполняются обоими совместно, без выделения отдельного человека под них).

Каждый временной сегмент плана разбит именно на два таких трека с явными **точками синхронизации** (см. диаграмму ниже), а не с передачей результата от одного разработчика другому — так ни один из двух разработчиков не простаивает в ожидании результата второго.

Ниже план разбит на 5 временных сегментов, заданных в **процентах от общего бюджета времени хакатона** (0–100%; точная длительность конкретного мероприятия не фиксируется в этом документе — проценты нужно пересчитать в часы/дни под фактическое расписание).

## 3. Сегменты плана

### Сегмент 1 — Bootstrap (0–15%)

**Трек A (ML/Data):**
- Разворачивает детектор ТС на готовых весах YOLOv8, проверяет детекцию и кроп/препроцессинг (OpenCV) на тестовых кадрах/видео.
- Поднимает FastReID «из коробки», прогоняет готовый бейзлайн (претрейн на VeRi-776) без дообучения — получает первые числа по mAP/Rank-1/Rank-5 как опорную точку для сравнения на всех дальнейших итерациях.
- Скачивает и проверяет структуру VeRi-776 (и при наличии времени — VeRi-Wild/VehicleID).

**Трек B (Backend/Infra):**
- Настраивает репозиторий: структура проекта, README-скелет, зависимости.
- Поднимает инфраструктуру через Docker: Qdrant (или FAISS) и Postgres/SQLite — на этом этапе можно с тестовыми/фиктивными данными.
- Готовит черновые контракты API (`/extract`, `/search`, `/register_plate`), чтобы не ждать готовой модели для старта разработки backend.

**Точка синхронизации (m1, 15%):** черновые контракты API и предварительный формат эмбеддинга согласованы между треками — дальше оба трека расходятся на независимую работу.

**Definition of done:**
- Детектор находит и вырезает ТС на тестовых изображениях.
- FastReID-бейзлайн запускается и выдаёт эмбеддинги; получены первые метрики mAP/Rank-1 на VeRi-776 (даже если ниже целевых).
- Qdrant/FAISS и Postgres/SQLite подняты в Docker и доступны обоим разработчикам.
- Репозиторий инициализирован, README содержит инструкцию по запуску окружения.
- Черновые схемы API согласованы.

---

### Сегмент 2 — Core Build (15–45%)

**Трек A (ML/Data):**
- Дообучение/файнтюн re-id модели (OSNet/ResNet50, опционально TransReID) под целевые условия задачи; при наличии времени — доменная адаптация через VehicleX или дополнительные датасеты (VeRi-Wild, VehicleID, CityFlow/AI City Track 2).
- Обучение атрибутных голов (цвет кузова, тип/класс ТС) с опорой на CompCars/Stanford Cars/BoxCars116k.

**Трек B (Backend/Infra):**
- Разработка REST API на FastAPI: эндпоинты `/extract`, `/search`, `/register_plate` — сначала на моках модели (заглушки вместо реальных эмбеддингов).
- Интеграция каркаса полного пайплайна (детектор → кроп → экстрактор → БД) с заменяемым модельным слоем, чтобы переключение мок → реальная модель не требовало переписывания API.

**Точка синхронизации (m2, 45%):** финальный (или близкий к финальному) формат эмбеддинга и схема метаданных зафиксированы Треком A → Трек B переключает backend с мока на реальную модель.

**Definition of done:**
- Дообученная re-id модель показывает измеримое улучшение (или обоснованно не показывает — тогда фиксируется решение остаться на бейзлайне) относительно метрик Сегмента 1.
- Атрибутные головы выдают предсказания цвета/типа кузова с адекватной точностью на валидационном сплите.
- API endpoints работают end-to-end на моках, каркас интеграции готов к подключению реальной модели.

---

### Сегмент 3 — Данные и фильтры (45–65%)

**Трек A (ML/Data):**
- Наполнение Vector DB: извлечение эмбеддингов по галерее, загрузка векторов в Qdrant/FAISS, синхронизация метаданных (координаты, время, атрибуты, номер при наличии) в Postgres/SQLite.
- Итеративная оценка качества (mAP, Rank-1/Rank-5, CMC-кривая) на каждой значимой итерации модели.

**Трек B (Backend/Infra):**
- Реализация re-ranking (k-reciprocal encoding) поверх базового поиска по косинусной близости.
- Реализация spatio-temporal фильтров кандидатов (отсечение по времени/геолокации камер).
- Логика подсказки вероятного номера: агрегация OCR-результатов (EasyOCR/PaddleOCR) по кластеру и выбор наиболее вероятного варианта.

**Точка синхронизации (m3, 65%):** API стабилен (эндпоинты + re-ranking + фильтры работают на реальной модели) → Трек B может без риска переделок начинать frontend, Трек A продолжает независимо работать над качеством модели.

**Definition of done:**
- Vector DB наполнена эмбеддингами и метаданными в объёме, достаточном для демонстрации поиска.
- Re-ranking и spatio-temporal фильтры подключены и влияют на порядок/состав кандидатов в `/search`.
- Логика подсказки номера возвращает результат по тестовому кластеру событий.
- Пайплайн проходит сквозной прогон на реальной модели: фото на входе → топ-N похожих ТС со score на выходе.

---

### Сегмент 4 — Демо и метрики (65–85%)

**Трек A (ML/Data):**
- Финальный замер метрик качества (mAP, Rank-1/Rank-5, CMC-кривая) и прикладных метрик (latency инференса, precision top-1 кандидата) на итоговом query/gallery сплите.
- Подготовка сравнительных графиков «бейзлайн vs дообученная модель» для питча.

**Трек B (Backend/Infra/Frontend):**
- Разработка demo-UI (Streamlit/Gradio): загрузка фото ТС, вызов backend API, отображение топ-N похожих машин с score, атрибутов и (при наличии) подсказки номера.
- Базовая визуализация детекции/кропа для наглядности на защите.
- Проверка UI на реалистичных сценариях (разные ракурсы/условия освещения).

**Definition of done:**
- Зафиксированы метрики качества и latency, готовы графики для слайдов.
- UI запускается локально/в Docker одной командой; пользователь может загрузить фото и получить топ-N похожих ТС со score.
- UI не падает на нетипичных входных данных (пустое фото, отсутствие ТС в кадре).

---

### Сегмент 5 — Полировка и сдача (85–100%, совместно)

**Точка синхронизации (m4, 85%):** оба трека сходятся для совместной финальной сборки — с этого момента задачи не делятся по трекам.

**Что делаем вместе:**
- Финальный код-ревью, чистка репозитория от временных/отладочных файлов.
- Финализация README: инструкция по запуску, описание API, известные ограничения.
- Подготовка слайдов/питча с зафиксированными метриками.
- Запись видео-демо как резервного варианта на случай технических сбоев во время очной презентации.

**Definition of done:**
- README и репозиторий в состоянии, пригодном для стороннего ревью.
- Слайды/питч готовы и содержат метрики.
- Видео-демо записано и проверено на воспроизведение без интернета/зависимостей.

| Разработчик | Покрывает роли из условия задачи | Основные задачи | Сегменты |
|---|---|---|---|
| **Инженер A — ML/Data** | ML-инженер + специалист по работе с данными | Детектор и бейзлайн FastReID, дообучение Re-ID модели, атрибутные головы, датасеты и сплиты, наполнение Vector DB эмбеддингами, замер метрик качества | 1–5 |
| **Инженер B — Backend/Infra/Frontend** | Backend-разработчик | Репозиторий и Docker-инфраструктура, REST API (FastAPI), интеграция пайплайна, re-ranking, spatio-temporal фильтры, логика подсказки номера, demo-UI | 1–5 |

## 6. Риски и как их снижать

| Риск | Как снижаем |
|---|---|
| Domain gap: публичные датасеты (VeRi-776 и др.) не соответствуют реальным условиям задачи | Заранее изучить данные, которые предоставят организаторы; по возможности собрать и разметить небольшой локальный валидационный сет, отражающий целевые условия, и оценивать модель именно на нём, а не только на паблик-бенчмарках |
| Нехватка времени на дообучение re-id модели | Резервный план: если дообучение не укладывается в срок, использовать чистый претрейн FastReID (bagoftricks baseline) без fine-tune и честно показать метрики «as is» на питче, не выдавая их за результат дообучения |
| Ложные срабатывания на похожих машинах одного цвета/класса | Смягчать через spatio-temporal фильтры кандидатов (отсечение по времени/геолокации) и через атрибутные признаки (цвет, тип кузова) как дополнительный сигнал ранжирования, а не полагаться только на визуальный эмбеддинг |
| Рассинхронизация двух разработчиков из-за параллельной работы | Держаться четырёх точек синхронизации (m1–m4 на диаграмме): контракт API/эмбеддинга фиксируется на m1 и не меняется без согласования; переключение mock → real модель — только на m2; frontend стартует только после m3, когда API уже стабилен |
| Технические сбои во время очной демонстрации (сеть, зависимости, железо) | Заранее записанное видео-демо как резервный вариант, который можно показать вместо живой демонстрации |
