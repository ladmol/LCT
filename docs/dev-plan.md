# План разработки — Vehicle Re-ID (Falcon Tech, ЛЦТ 2026)

## 1. Общий подход

Задача решается за ограниченное время хакатона, поэтому ключевой принцип — **не обучать ничего с нуля**. Берём готовый тулбокс FastReID с претрейн-весами на VeRi-776/VehicleID, при необходимости дообучаем/адаптируем под целевые данные, а не строим re-id модель заново. Детектор (YOLOv8) и OCR (EasyOCR/PaddleOCR) также используются как готовые претрейн-компоненты без обучения с нуля.

Второй принцип — **параллельная разработка, а не конвейер**: backend-сервис и интеграционный пайплайн разрабатываются одновременно с работой над ML-моделью, на моках (заглушках вместо реальных эмбеддингов/поиска), а не после того, как модель будет готова. Это снижает риск того, что к моменту сдачи не останется времени на интеграцию.

Третий принцип — **MVP-first**: сначала собирается сквозной работающий путь «фото → детекция → эмбеддинг → поиск похожих → топ-N с score», пусть и на бейзлайн-качестве, и только потом идёт улучшение метрик, атрибутов, re-ranking и UI. Работающий, пусть и грубый, end-to-end пайплайн на ранней стадии — приоритет выше, чем точность отдельного компонента.

Ниже план разбит на 5 фаз, заданных в **процентах от общего бюджета времени команды** на хакатоне (точная длительность хакатона не фиксируется в этом документе — проценты нужно пересчитать в часы/дни под фактическое расписание конкретного мероприятия).

## 2. Фазы разработки

### Фаза 1 — Bootstrap (~15% времени)

**Что делаем:**
- Разворачиваем детектор ТС на готовых весах YOLOv8, проверяем детекцию и кроп/препроцессинг (OpenCV) на тестовых кадрах/видео.
- Поднимаем FastReID «из коробки», прогоняем готовый бейзлайн (претрейн на VeRi-776) без дообучения — получаем первые числа по mAP/Rank-1/Rank-5, чтобы иметь опорную точку для сравнения на всех дальнейших итерациях.
- Настраиваем репозиторий: структура проекта, README-скелет, требования к окружению (requirements/зависимости), CI-заготовка при необходимости.
- Поднимаем инфраструктуру через Docker: Qdrant (или FAISS-сервис) и Postgres/SQLite для метаданных — на этом этапе можно с тестовыми/фиктивными данными.
- Фиксируем контракты API (черновые схемы `/extract`, `/search`, `/register_plate`), чтобы backend мог стартовать параллельно, не дожидаясь готовой модели.

**Кто отвечает:** Инженер ML — детектор, FastReID, первый прогон бейзлайна. Бэкенд-разработчик — репозиторий, Docker-инфраструктура, черновые контракты API. Менеджер проекта — координация, фиксация плана и зон ответственности. Специалисты по данным — подготовка/скачивание VeRi-776 и проверка её структуры.

**Зависимости:** нет (стартовая фаза), но результаты (контракты API, поднятая инфраструктура) — база для фаз 2 и 3.

**Definition of done:**
- Детектор находит и вырезает ТС на тестовых изображениях.
- FastReID-бейзлайн запускается и выдаёт эмбеддинги; получены первые метрики mAP/Rank-1 на VeRi-776 (даже если они ниже целевых).
- Qdrant/FAISS и Postgres/SQLite подняты в Docker и доступны по сети команды.
- Репозиторий инициализирован, README содержит инструкцию по запуску окружения.
- Черновые схемы API согласованы между ML и backend.

---

### Фаза 2 — Core ML (~30% времени)

**Что делаем:**
- Дообучение/файнтюн re-id модели (OSNet/ResNet50, опционально TransReID) под целевые условия задачи, при наличии — с использованием доменной адаптации через VehicleX или дополнительных датасетов (VeRi-Wild, VehicleID, CityFlow/AI City Track 2).
- Обучение атрибутных голов (цвет кузова, тип/класс ТС) — с опорой на CompCars/Stanford Cars/BoxCars116k как источники fine-grained разметки.
- Формирование пайплайна наполнения Vector DB: извлечение эмбеддингов по галерее, загрузка векторов в Qdrant/FAISS, синхронизация метаданных (координаты, время, атрибуты, при наличии — номер) в Postgres/SQLite.
- Итеративная оценка качества (mAP, Rank-1/Rank-5, CMC-кривая) на каждой значимой итерации модели, сравнение с бейзлайном из Фазы 1.

**Кто отвечает:** Инженер ML — дообучение, атрибутные головы, метрики. Специалисты по данным — подготовка обучающих/валидационных сплитов, разметка/чистка данных, наполнение метаданными. Бэкенд-разработчик на этой фазе занят параллельно Фазой 3 (см. ниже), но синхронизируется по формату эмбеддингов/метаданных, чтобы Vector DB было совместимо со схемой API.

**Зависимости:** использует инфраструктуру (Docker, Qdrant/Postgres) из Фазы 1. Идёт **параллельно** с Фазой 3 — обе фазы требуют регулярной синхронизации по контракту данных (формат вектора, размерность эмбеддинга, состав метаданных).

**Definition of done:**
- Дообученная re-id модель показывает измеримое улучшение (или обоснованно не показывает — тогда фиксируется решение остаться на бейзлайне) относительно метрик Фазы 1.
- Атрибутные головы выдают предсказания цвета/типа кузова с адекватной точностью на валидационном сплите.
- Vector DB наполнена эмбеддингами и метаданными в объёме, достаточном для демонстрации поиска.
- Зафиксирован финальный (или близкий к финальному) формат эмбеддинга и схема метаданных, согласованные с backend.

---

### Фаза 3 — Backend & integration (~30% времени)

**Что делаем:**
- Разработка REST API на FastAPI: эндпоинты `/extract` (получение эмбеддинга/атрибутов по изображению), `/search` (поиск похожих ТС по вектору в Qdrant/FAISS с фильтрами), `/register_plate` (привязка/регистрация номера к кластеру событий).
- Интеграция полного пайплайна: детектор → кроп → экстрактор эмбеддингов → атрибутные головы → запись/поиск в Vector DB — сначала на моках модели (Фаза 1), затем переключение на реальную дообученную модель по мере готовности Фазы 2.
- Реализация re-ranking (k-reciprocal encoding) поверх базового поиска по косинусной/евклидовой близости.
- Реализация spatio-temporal фильтров кандидатов (отсечение по времени/геолокации камер), снижающих число ложных совпадений среди визуально похожих ТС.
- Логика подсказки вероятного номера для кластера событий: агрегация OCR-результатов (EasyOCR/PaddleOCR) по кластеру треков/похожих объектов и выбор наиболее вероятного варианта номера.
- Автогенерация Swagger/OpenAPI-документации силами FastAPI, проверка её актуальности.

**Кто отвечает:** Бэкенд-разработчик — основной исполнитель API и интеграции. Инженер ML — консультирует по интерфейсу вызова модели и Vector DB, помогает с переключением с мока на реальную модель. Менеджер проекта — следит за синхронизацией контрактов между Фазами 2 и 3.

**Зависимости:** стартует сразу после Фазы 1 (использует Docker-инфраструктуру и черновые контракты API), идёт **параллельно** с Фазой 2, а не после неё. Полная интеграция реальной модели (а не мока) зависит от готовности артефактов Фазы 2 (обученные веса, финальный формат эмбеддинга).

**Definition of done:**
- Все три эндпоинта (`/extract`, `/search`, `/register_plate`) реализованы и работают на реальной модели (не на моке).
- Swagger-документация доступна и отражает актуальные схемы запросов/ответов.
- Re-ranking и spatio-temporal фильтры подключены и влияют на порядок/состав кандидатов в `/search`.
- Логика подсказки номера возвращает результат по тестовому кластеру событий.
- Пайплайн проходит сквозной прогон: фото на входе → топ-N похожих ТС со score на выходе.

---

### Фаза 4 — Frontend/демо-интерфейс (~15% времени)

**Что делаем:**
- Разработка простого demo-UI (Streamlit/Gradio): загрузка фотографии ТС, вызов backend API, отображение топ-N похожих машин с score, отображение атрибутов и (при наличии) подсказки номера.
- Базовая визуализация результатов детекции/кропа для наглядности на питче.
- Проверка UI на реалистичных сценариях (несколько тестовых фото, разные ракурсы/условия освещения).

**Кто отвечает:** Бэкенд-разработчик (или тот, кто свободен к этому моменту) — реализация UI поверх готового API. Менеджер проекта — прогон демо-сценариев глазами «жюри», сбор обратной связи.

**Зависимости:** требует рабочего API из Фазы 3 (минимум — эндпоинты `/extract` и `/search`).

**Definition of done:**
- UI запускается локально/в Docker одной командой.
- Пользователь может загрузить фото и получить топ-N похожих ТС со score в интерфейсе.
- UI не падает на нетипичных входных данных (пустое фото, отсутствие ТС в кадре и т.п. обрабатываются без краша).

---

### Фаза 5 — Полировка и подготовка к сдаче (~10% времени)

**Что делаем:**
- Финальный замер метрик качества (mAP, Rank-1/Rank-5, CMC-кривая) и прикладных метрик (latency инференса, latency поиска, precision top-1 кандидата на итоговом query/gallery сплите).
- Финализация README: инструкция по запуску, описание API, известные ограничения.
- Подготовка слайдов/питча с зафиксированными метриками.
- Запись видео-демо как резервного варианта на случай технических сбоев во время очной презентации.
- Финальный код-ревью, чистка репозитория от временных/отладочных файлов.

**Кто отвечает:** Менеджер проекта — сборка питча и координация. Инженер ML — финальные метрики и их интерпретация для слайдов. Бэкенд-разработчик — финализация README и стабильности сервиса. Специалисты по данным — при необходимости добивают/проверяют финальный валидационный сплит для честных метрик.

**Зависимости:** требует завершённых (хотя бы в базовом объёме) Фаз 2, 3 и 4.

**Definition of done:**
- Зафиксированы и задокументированы финальные метрики качества и latency.
- README и репозиторий в состоянии, пригодном для стороннего ревью.
- Слайды/питч готовы и содержат метрики.
- Видео-демо записано и проверено на воспроизведение без интернета/зависимостей.

## 5. Риски и как их снижать

| Риск | Как снижаем |
|---|---|
| Domain gap: публичные датасеты (VeRi-776 и др.) не соответствуют реальным условиям задачи | Заранее изучить данные, которые предоставят организаторы; по возможности собрать и разметить небольшой локальный валидационный сет, отражающий целевые условия, и оценивать модель именно на нём, а не только на паблик-бенчмарках |
| Нехватка времени на дообучение re-id модели | Резервный план: если дообучение не укладывается в срок, использовать чистый претрейн FastReID (bagoftricks baseline) без fine-tune и честно показать метрики «as is» на питче, не выдавая их за результат дообучения |
| Ложные срабатывания на похожих машинах одного цвета/класса | Смягчать через spatio-temporal фильтры кандидатов (отсечение по времени/геолокации) и через атрибутные признаки (цвет, тип кузова) как дополнительный сигнал ранжирования, а не полагаться только на визуальный эмбеддинг |
| Рассинхронизация ML и backend из-за параллельной разработки | Зафиксировать контракт (формат эмбеддинга, схема метаданных, схемы API) как можно раньше в Фазе 1 и не менять его без согласования; регулярные синхронизации между Фазами 2 и 3 |
| Технические сбои во время очной демонстрации (сеть, зависимости, железо) | Заранее записанное видео-демо как резервный вариант, который можно показать вместо живой демонстрации |
