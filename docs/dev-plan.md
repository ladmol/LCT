# План разработки

Команда из двух человек, два параллельных трека:

- **A — ML/Data:** модель, валидация, порог, артефакты сдачи.
- **B — Backend/Infra/Frontend:** сервисы, инференс-рантайм, Docker, UI, документация.

Архитектура — [`architecture.md`](architecture.md), технологии и версии — [`tech-stack.md`](tech-stack.md), ТЗ — [`task.md`](task.md).

## Принципы

1. **Сначала рабочий путь от начала до конца, потом качество.** Первая цель — `predict`, который из `test_query.csv` + `test_gallery.csv` выдаёт три валидных файла на предобученной модели без дообучения. Всё дальнейшее — итерации поверх работающего пути.
2. **Приоритет по весам оценки.**
   - mAP (45%) и скорость (20%) важнее всего остального.
   - Режим отказа (10%) делается на той же валидации почти бесплатно.
   - UI, Grad-CAM и ANN на 10⁶ дают 0 баллов (тай-брейкеры) и делаются в последнюю очередь.
3. **Скорость против точности — замером.**
   - Большая и малые модели учатся одним кодом.
   - Малую везём, если её mAP@10 не более чем на 5% относительно ниже большой (`tech-stack.md` §2.3).
   - Все оценки времени из документации — гипотезы до первого замера.
4. **Функциональный паритет.** Геометрия препроцессинга общая (`reid_core`). Метрики считаются только через `predict` → `evaluate.py`. Паритет `/v1/embed` и `predict` проверяется тестом (`architecture.md` §4.9).
5. **Метрики — эталонным скриптом.** Наш `eval` не пересчитывает метрики сам: он выгружает валидационный сплит в формате организаторов (`val_ground_truth.csv`: `image_id, vehicle_id, camera_id, split`) и запускает [`data/specs/evaluate.py`](../data/specs/evaluate.py). Протокол — §4.8 архитектуры.
6. **Воспроизводимость с первого дня.**
   - Все веса и датасеты с лицензиями записываются в Readme сразу при появлении.
   - Итоговый образ работает без сети.
   - Используем только веса без гейтинга; внешние датасеты — только после ответа организаторов.

## Фазы

Длительность — в процентах от времени хакатона: пересчитать в дни под фактическое расписание.

| Фаза | % времени | Трек A — ML/Data | Трек B — Backend/Infra/Frontend |
|---|---|---|---|
| **0. Сквозной бейзлайн** | 0–15 | Кэш кропов; кросс-камерный open-set сплит с дистракторами (§6.1 архитектуры); `eval` поверх `evaluate.py`. CLIP ViT-B/16 без дообучения → `predict` → три файла. **Первые замеры на своём GPU:** декодирование 1080p (CPU / nvJPEG), сеть FP16 при батче 1 и в пакете | uv workspace (`reid`, `services/*`), ruff + pytest + CI; `docker-compose.yml` с `db` (PostgreSQL 18 + pgvector); заглушки `inference` (случайные L2-векторы размерности 512) и `api` с OpenAPI |
| **1. Модели** | 15–45 | Дообучение большой модели (CLIP ViT-B/16; SigLIP 2 для сравнения) и 2–3 малых (DINOv2 ViT-S, ConvNeXt-T, R50-IBN) одним кодом. k-reciprocal re-ranking, тюнинг k1/k2. Таблица «mAP@10 против latency/FPS» → решение на **m2** | Настоящий `inference`: nvImageCodec, ONNX → TensorRT с **сборкой engine при старте** и кэшем, fallback на PyTorch FP16, micro-batcher, CUDA Graph для батча 1. `api`: `/v1/embed`, `/v1/search`, `/v1/gallery*`, загрузка галереи. Контейнер `predict` без сети |
| **2. Отказ и скорость** | 45–70 | Дистилляция — **только если** малая модель не прошла бюджет. Офлайн- и онлайн-калибраторы, τ по F1, кривые PR/F1/TNR. Проба FP8/INT8 (ModelOpt) с ограничением падения mAP@10 в 0.5 п. | `benchmark` в двух режимах («кроп → вектор», «JPEG + bbox → вектор»): батч 1 p50/p95/p99 и устойчивый FPS с RSS/VRAM. Сборка образов `cu126`/`cu130`. Тест паритета. `confidence`/`refused` в API. Веса в git + `SHA256SUMS` |
| **3. Продукт и тай-брейкеры** | 70–85 | Разбор ошибок: ракурс, ночь, перекрытия, одинаковые модели машин. При запасе времени — промпт-этап CLIP-ReID, голова ориентации | UI: загрузка, bbox, выдача, отказ, экспорт CSV. Grad-CAM (`/v1/explain`). Бенчмарк pgvector против FAISS на 10⁶ |
| **4. Сдача** | 85–100 | Финальные артефакты, метрики и обоснование τ в Readme | Прогон «чистый клон → `docker compose up`» на чистой машине с GPU (включая сборку engine с нуля), Readme, презентация |

## Точки синхронизации

| Точка | Когда | Что фиксируется |
|---|---|---|
| **m1** | конец фазы 0 | **D = 512** и формат вектора (float32, L2). Интерфейс `reid_core`: `preprocess(image, bbox)`, `embed(batch)`, `rank(q, g)`, `calibrate(...)`. Контракт API (§5 архитектуры). Формат артефакта модели: ONNX + safetensors (шарды < 100 МБ, без LFS) + калибраторы JSON + `SHA256SUMS`. Layout `predict` (пути, выходы) |
| **m2** | середина фазы 1 | Какую модель везём (большую или малую) и её `input_size`. Решение — по таблице «mAP@10 против скорости» и бюджету 5% |
| **m3** | конец фазы 2 | Итоговые веса, точность вычислений (FP16 / FP8 / INT8), τ; `api`, `predict` и `benchmark` работают на одном артефакте; выбран `CUDA_FLAVOR` (если организаторы сообщили GPU и драйвер) |
| **m4** | начало фазы 4 | Код заморожен; дальше только документация и презентация |

Между точками треки не ждут друг друга: B работает на заглушке `inference`, A — на своих скриптах. Благодаря фиксированному D на m1 смена модели на m2 не трогает работу трека B.

## Критерии готовности (чек-лист сдачи)

**Артефакты (ТЗ §8, README датасета)**
- [ ] `submission.csv` без заголовка: `query_id, gallery_id_1..10` (или top-K > 10, если организаторы подтвердят), одна строка на каждую строку `test_query.csv`.
- [ ] `embeddings.npy`: `float32 [N_query + N_gallery, 512]` (на публичной части 1110 + 750), сначала query, затем gallery, в порядке файлов.
- [ ] `candidates.csv` с заголовком: `query_id, gallery_id, confidence`; верхний кандидат совпадает с первым в `submission.csv`; запросы с отказом не дают строк.
- [ ] Все три файла проходят `data/specs/evaluate.py` на валидации без предупреждений (нет неизвестных и повторных `gallery_id`, нет пропущенных запросов).
- [ ] `predict` запускается одной командой в изолированном окружении без сети и принимает пути к произвольным CSV (закрытая часть теста).

**Качество**
- [ ] mAP@10, Rank-1, Rank-5, mINP на валидации (кросс-камерно, open-set) — в Readme, для большой и итоговой модели.
- [ ] F1, TNR, PR-AUC при выбранном τ + кривые + обоснование τ — в Readme.

**Производительность**
- [ ] Суммарный размер весов ≤ 2 ГБ.
- [ ] `benchmark` в обоих режимах: батч 1 (p50/p95/p99) и устойчивый FPS в пакете; нет OOM и роста памяти на полном тесте.
- [ ] TensorRT-engine собирается с нуля на чистой машине; fallback на PyTorch FP16 проверен.

**Инженерия (ТЗ §6, §12)**
- [ ] `docker compose up` поднимает `db`, `inference`, `api`, `frontend` без ручных шагов.
- [ ] OpenAPI (Swagger) доступен из `api` и `inference`.
- [ ] Тест паритета `/v1/embed` и `predict` зелёный.
- [ ] Readme: архитектура, методы, инструкция сборки, метрики, обоснование порога, полный список библиотек, весов и датасетов с версиями **и лицензиями**.
- [ ] Код обучения в репозитории и воспроизводим (конфиги, сплиты, seed).

**Защита (ТЗ §11)**
- [ ] Презентация:
  - выбор backbone и его обоснование, включая таблицу «точность против скорости» и почему не DINOv3;
  - как решали ракурс и освещение;
  - пользовательский путь;
  - план масштабирования;
  - честный разбор ошибок с примерами.

## Риски

| Риск | Что делаем |
|---|---|
| Переобучение на 1 541 ID train | Сильная предобученная инициализация, open-set валидация по ID, ранняя остановка по mAP@10 |
| Порог τ, подобранный на валидации, не переносится на закрытый тест | Калибровка вероятностей вместо «сырого» порога сходства, проверка устойчивости τ по фолдам и бутстрепу при разных долях дистракторов |
| Малая модель не укладывается в бюджет точности | Дистилляция в фазе 2; если не помогло — вопрос пользователю, по умолчанию везём большую |
| GPU или драйвер организаторов несовместимы с нашей сборкой CUDA | `CUDA_FLAVOR` как build-аргумент, два проверенных образа; вопрос организаторам в первый день |
| Сборка TensorRT-engine падает на их GPU | Автоматический fallback на PyTorch FP16; проверка в фазе 4 на чистой машине |
| Внешние датасеты не признают «открытыми» | Базовая линия обучается только на train организаторов; внешние данные — усиление, а не зависимость |
| Модель выучит остатки номерного знака | Маскирование зоны номера как аугментация; Grad-CAM-проверка, что внимание не концентрируется на номере |
| Разные декодеры JPEG при обучении и инференсе | Функциональный паритет: метрики только через `predict`, тест паритета эмбеддингов |
| Не успеваем к сдаче | Сквозной бейзлайн в фазе 0 и сохранение валидных артефактов после каждой итерации; тай-брейкеры — только после m3 |
| Открытые вопросы к организаторам (§10 архитектуры) остаются без ответа | Задать в первый день; до ответа — консервативные допущения, записанные в Readme |
